ATTACK 1 [MAJOR] The "§6 fini quand" grep cannot check the "every number comes from a script" rule
Where: §4, §6 Résultats, "Fini quand : `grep -nE "[0-9]+[,.][0-9]+" Report/Affinity_propagation_rapport.qmd` ne trouve hors chunks aucun chiffre de résultat écrit à la main"
Problem: This is the plan's only mechanical check for the CLAUDE.md rule "chaque chiffre du texte doit correspondre à une sortie réellement produite par un script", and it fails both ways. (a) False positives: the same plan tells the authors to type decimals by hand in other parts, for example §5 "pas de 0,05", "λ ∈ {0,5 ; 0,7 ; 0,9}" and §4 "`lam = 0.9`" with "λ = 0,5 dans l'article". The grep reads the whole file, not only §6, so it can never come back empty. (b) False negatives: whole-number results do not match the pattern. Hand-typed "9 clusters", "149 clusters", "210 itérations" or the counts of the q = 0 contingency table (50/41/15/9/35), all numbers the plan itself quotes in §1.1, would pass. In practice the "fini quand" test either always fails or lets the exact error it is meant to catch slip through.

ATTACK 2 [MAJOR] The k used for the "k égal" comparison is never fixed, and the open choice invites label leakage
Where: §4, §5 "comparateurs à **k imposé par AP**" ; §6 block 2 "tableau à k égal : critère p-médiane, ARI, silhouette et temps pour AP, `pam` et K-means (Q3)"
Problem: The plan's own run (re-checked: apcluster 1.4.14, seed 1234) shows that AP's k depends on q: 9 at the default (median), 5 for q = 0.05–0.2, 3 for q = 0 and 149 for q = 1. The plan never says which q sets the k for the Q3 table: the default, every point of the grid, or something else. The only k at which the comparison looks natural on Iris is 3, and §1.1 Enjeu 4 itself says that picking q = 0 for that reason "serait régler AP à l'aide des espèces". A user acting on §5–6 has to guess, and the most likely guess (k = 3) is the leakage the plan forbids. The Q3 headline table is therefore not specified well enough to be reproducible ("un lecteur peut relancer chaque expérience avec les seuls paramètres écrits", §5).

ATTACK 3 [MAJOR] The stability protocol cannot be computed as written
Where: §4, §6 block 4 "stabilité : 50 sous-échantillons à 80 %, ARI moyen entre partitions, AP comparé à K-means"
Problem: ARI compares two partitions of the same set of points. Two 80 % subsamples share only about 64 % of the points on average, and AP (`apcluster`) has no way to assign points left out of its run. The plan does not say whether the ARI is computed on the intersection, against the full-data partition or by another rule. It also ignores that with the median preference AP's k changes from one subsample to the next, while K-means needs a fixed k (which one?). Two people following this line would get different numbers. Since the plan sends stability to the 07/11 slot with "résultats négatifs présents" as the only check, nothing would catch this.

ATTACK 4 [MINOR] "Hervé n'a aucun commit" is stated as a fact although the author of the initial commit is not identified
Where: En bref, point 4 "Hervé n'a aucun commit" ; §1.2, row Git, "1 commit initial (`dea0014`), 0 commit de Hervé"
Problem: `git remote -v` shows that the GitLab repository belongs to the namespace `dea0014` (https://gitlab-mi.univ-reims.fr/dea0014/affinity_propagation.git). The initial commit e9ab1b1 is signed `dea0014`. The plan never establishes whether this university login is Hervé's or Marie's, yet in its headline risk it counts the commit as nobody's. The task requires "Ne rien présenter comme vérifié sans l'avoir vérifié". This should be marked "non vérifié: identité de dea0014". The point matters because it is put forward as the "risque majeur pour la note individuelle".
